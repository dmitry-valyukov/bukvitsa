# Модель книги FB3: решения

Модуль: `bukvitsa.fb3` (`FB3/src/*.ixx`).

## Слои

```
файл .fb3
   │  OpcPackage        — Windows Packaging API (msopc.h), COM
   ▼
части пакета (description.xml, body.xml, картинки)
   │  wxl::xml          — разбор без копирования, дерево видов
   ▼
дерево узлов XML
   │  DocumentBuilder   — типизация, разрешение связей, позиции символов
   ▼
Document: Description + дерево Node + картинки + сноски
   │
   ▼  Typography верстает, Reader показывает
```

## Контейнер: Windows Packaging API, а не свой разбор zip

FB3 — пакет OPC (ECMA-376 Part 2), тот же контейнер, что у .docx, и Windows
читает его штатно: COM-компонент из `msopc.h` разбирает `[Content_Types].xml`,
файлы связей и правила именования частей. Это не мелочь: официальный пример
`hardcore_file_structure` из репозитория спецификации нарочно ломает наивные
реализации — кириллические имена частей с процентным кодированием, верхний
регистр в `_RELS`, часть без расширения с типом, объявленным только в
Content_Types. Всё это Packaging API отрабатывает сам.

Навигация — исключительно по типам содержимого и типам связей; пути не
угадываются нигде, потому что формат имена частей не фиксирует:

| Что | Значение |
|---|---|
| Тип содержимого тела | `application/fb3-body+xml` |
| Тип содержимого описания | `application/fb3-description+xml` |
| Связь пакета → описание | `http://www.fictionbook.org/FictionBook3/relationships/Book` (заглавная B!) |
| Связь описания → тело | `http://www.fictionbook.org/FictionBook3/relationships/body` |
| Связь тела → картинка | `http://www.fictionbook.org/FictionBook3/relationships/image` |
| Обложка | OPC-связь миниатюры: `http://schemas.openxmlformats.org/package/2006/relationships/metadata/thumbnail` |

`<img src="…">` в теле ссылается **на Id связи** в `.rels`-файле, а не на путь
к файлу.

Про WinRT: архивов он не читает вовсе — `Windows.Storage.Compression` это
потоковый компрессор, а не zip. Так что OPC API и есть «средство Windows»,
просто COM, а не WinRT; для приложения на C++/WinRT разницы нет.

## XML: wxl.xml с текстовыми узлами

Читатель XML — `wxl::xml`: дерево целиком из видов в буфер документа, арена,
интрузивные списки. Книга проходит путь от файла до вёрстки без единого
копирования текста.

Существенны текстовые узлы: для `<p>Начало <strong>жирный</strong> конец</p>`
недостаточно знать, что у абзаца есть текст и ребёнок `strong`, — важно, что
было до него, а что после. Смешанное содержимое — это ровно то, из чего
состоит книжный абзац, и `wxl.xml` отдаёт его текстовыми узлами в порядке
документа. Пробельные узлы при этом **не** отбрасываются: пробел между `</p>`
и `<p>` незначим, а между текстом и `<strong>` — значим, и различить их может
только тот, кто знает семантику элементов. Это делает слой FB3.

Побочно: необъявленный префикс пространства имён `wxl.xml` не отвергает, а
оставляет имя вне пространств — осознанное отступление, записано в её TODO.
Для FB3 это работает: тело пишется в пространстве по умолчанию, префикс есть
только у `xlink:href`.

## Дерево: один тип узла, вид перечислением

Никаких иерархий классов и виртуальных функций: обход книги — это `switch`
по `kind()`. Причина не в экономии vptr (хотя в книге узлов десятки тысяч),
а в том, что вёрстка всё равно обрабатывает виды узлов по-разному и таблица
переходов компилятора здесь честнее диспетчеризации.

Атрибуты разобраны заранее в типизированные структуры (`SectionData`,
`DivData`, `ImageData`, `NoteRefData`, …) и лежат **рядом** с узлом, а не
внутри него: нагрузку несёт меньшинство узлов, и `Node` не должен раздуваться
до размера самого сложного из них. Разбор при загрузке, а не при вёрстке —
книгу верстают заново при каждой смене кегля, и повторно разбирать `float`
или `colspan` незачем.

Что разрешается один раз при загрузке и больше никогда:

- `<note href="n_1">` → указатель на соответствующий `NoteBody`;
- `<img src="rId7">` → индекс части в `Document::images()`;
- `ol`/`ul` → `List` с флагом, `th`/`td` → `TableCell` с флагом.

## Позиции: символы, а не страницы

Каждый узел несёт `charOffset()` — позицию первого своего символа в полной
книге; у секции сверх того `firstCharPos` из самого формата (FB3 хранит его
ради вырезанных пробных фрагментов). Это валюта закладок, прогресса и
восстановления места чтения: она не зависит ни от кегля, ни от размера окна,
ни от версии движка вёрстки — в отличие от номера страницы.

Обратный переход даёт `Document::nodeAtCharOffset()`. Позже к этому может
добавиться адресация вида «UUID секции + смещение» — она переживёт даже
переоткрытие книги в другом издании файла.

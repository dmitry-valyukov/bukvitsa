# Модель книги FB3: решения

Дата: 22.08.2026. Модуль: `bukvitsa.fb3` (`FB3/src/*.ixx`).

## Слои

```
файл .fb3
   │  OpcPackage        — Windows Packaging API (msopc.h), COM
   ▼
части пакета (description.xml, body.xml, картинки)
   │  wxl::xml::parser  — разбор без копирования, дерево видов
   ▼
дерево xml::element
   │  DocumentBuilder   — типизация, разрешение связей, позиции символов
   ▼
Document: Description + дерево Node + картинки + сноски
   │
   ▼  Typography верстает, Abajour показывает
```

## Контейнер: Windows Packaging API, а не свой разбор zip

FB3 — пакет OPC (ECMA-376 Part 2), тот же контейнер, что у .docx, и Windows
читает его штатно: COM-компонент из `msopc.h` разбирает `[Content_Types].xml`,
файлы связей и правила именования частей. Это не мелочь: официальный пример
`Hardcore file structure` из репозитория спецификации нарочно ломает наивные
реализации — кириллические имена частей с процентным кодированием, верхний
регистр в `_RELS`, часть без расширения с типом, объявленным только в
Content_Types. Всё это Packaging API отрабатывает сам.

Навигация — исключительно по типам содержимого и типам связей
(`.../relationships/Book` → description, `.../relationships/body` → body,
`.../relationships/image` → картинки, `src=` указывает на **Id связи**, а не
на файл). Пути не угадываются нигде.

Про WinRT: архивов он не читает вовсе — `Windows.Storage.Compression` это
потоковый компрессор, а не zip. Так что OPC API это и есть «средство Windows»,
просто COM, а не WinRT; для приложения на C++/WinRT разницы нет.

Запасной путь, если строгая проверка OPC отвергнет реальный файл из «дикого»
корпуса: libzip/minizip + свой слой OPC (~200–300 строк). Пока не нужен.

## XML: wxl.xml, с одной доработкой

Парсер из соседнего проекта подходит идеально: дерево целиком из
`string_view` в буфер документа, арена, интрузивные списки, 486 МБ/с. Книга
проходит путь от файла до вёрстки без единого копирования текста.

**Но:** сейчас текстовые куски элемента склеиваются в один `value()`, и
порядок текста относительно детей теряется. Для `<p>Начало <strong>жирный</strong>
конец</p>` получается `value() == "Начало  конец"` и ребёнок `strong` — узнать,
что было до, а что после, уже нельзя. Смешанное содержимое — это ровно то,
из чего состоит книжный абзац, поэтому без доработки FB3 не разобрать.

Доработка небольшая и не трогает существующего потребителя:

- в `options` добавляется `keep_text_nodes` (по умолчанию `false` — wxl.gen
  сохраняет прежнее быстрое поведение);
- добавляется `text_name` рядом с `comment_name = "!"` — узел-лист, имя
  которого не может носить элемент;
- в цикле содержимого накопленные куски сбрасываются в текстовый узел перед
  тем, как начать читать элемент-ребёнка, и ещё раз на закрывающем теге.
- пробельные узлы **не** отбрасываются: пробел между `</p>` и `<p>` незначим,
  а между текстом и `<strong>` — значим, и различить их может только тот, кто
  знает семантику элементов. Это делает слой FB3.

Побочно: `wxl.xml` не разрешает пространства имён (имена хранятся с
префиксами). Для FB3 это работает — тело пишется в пространстве по умолчанию,
префикс есть только у `xlink:href`, — но файл, где издатель объявил префикс
для пространства FB3, разобран не будет. Проверяем объявление на корне и
сообщаем внятной ошибкой, а не молчаливым непониманием.

## Дерево: один тип узла, вид перечислением

Никаких иерархий классов и виртуальных функций: обход книги — это `switch`
по `kind()`. Причина не в экономии vptr (хотя в книге узлов десятки тысяч),
а в том, что вёрстка всё равно обрабатывает виды узлов по-разному и таблица
переходов компилятора здесь честнее диспетчеризации.

Атрибуты разобраны заранее в типизированные структуры (`SectionData`,
`DivData`, `ImageData`, `NoteRefData`, …) и лежат **рядом** с узлом, а не
внутри него: нагрузку несёт меньшинство узлов, и `Node` не должен раздуваться
до размера самого сложного из них. Разбор при загрузке, а не при вёрстке —
книгу верстают заново при каждой смене кегля, и повторно разбирать `float`
или `colspan` незачем.

Что разрешается один раз при загрузке и больше никогда:

- `<note href="n_1">` → указатель на соответствующий `NoteBody`;
- `<img src="rId7">` → индекс части в `Document::images()`;
- `ol`/`ul` → `List` с флагом, `th`/`td` → `TableCell` с флагом.

## Позиции: символы, а не страницы

Каждый узел несёт `charOffset()` — позицию первого своего символа в полной
книге; у секции сверх того `firstCharPos` из самого формата (FB3 хранит его
ради вырезанных пробных фрагментов). Это валюта закладок, прогресса и
восстановления места чтения: она не зависит ни от кегля, ни от размера окна,
ни от версии движка вёрстки — в отличие от номера страницы.

Обратный переход даёт `Document::nodeAtCharOffset()`. Позже к этому добавится
адресация вида «UUID секции + смещение» — она переживает даже переоткрытие
книги в другом издании файла.

## Что дальше

1. Доработать `wxl.xml` (текстовые узлы) — это разблокирует всё остальное.
2. `OpcPackage` поверх Packaging API + тест на трёх официальных примерах,
   включая `Hardcore file structure`.
3. `DocumentBuilder`: xml-дерево → `Node`, разрешение связей, позиции.
4. `Description`.
5. Вертикальный срез: Typography верстает первый абзац настоящей книги.
